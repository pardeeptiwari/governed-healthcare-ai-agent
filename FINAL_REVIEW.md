### Claims root cause and options

`workflow.get_claim` makes a direct call through `Gateway.claim` when a claim ID is present. Date and service questions have no ID and use `Gateway.claim_pages`. `workflow.claims` consumes complete pagination for counts. `api.turn` propagates the request deadline to `Budget` and the gateway. The mock's `Handler._claims_gate` sleeps 1.5 seconds for each accepted request, returns 429 every seventh claim request, and advertises a one-second retry delay. `Handler._claims_page` caps pages at five and only supplies the next continuation. The brief requires a working budgeted slice and evaluation. It requires a proposed production design responsive to NFR-3. The observed default-profile behavior independently remains an assessment quality gap.

Direct lookup, intent-specific tool execution and deterministic calculations were already in place. The benchmark used local routing with no LLM calls. The optional live classifier remains for ambiguous intent. Requests share an HTTPX client. The mock handler uses the standard HTTP/1.0 response behavior, which limits connection reuse. Claim detail and policy retrieval are dependent because policy selection uses the returned claim. Page traversal is dependent because each continuation must be received and validated. Blind parallel offset requests would bypass the continuation contract. Evicting the cache, widening its freshness period, speculative prefetch, and increasing the deadline would not establish cold-path compliance. The new short-lived prefix cache eliminates some repeated reads when there is enough time to finish. It cannot guarantee a consistent snapshot if an offset-based source mutates mid-traversal. Counts never accept an incomplete prefix as a finished result.

The [before](evaluation/m11.1-before.json) and [after](evaluation/m11.1-after.json) reports used fresh isolated mock processes, fresh SQLite databases, the same 40 scripted conversations in the same order, the same Python environment, the same three-second allowance and deterministic classification. Timings span TestClient turn dispatch through response and exclude pre/post observer requests and deliberate replay probes. Call counts are application gateway attempts and exclude evaluation observer traffic. The [six-second diagnostic](evaluation/m11.1-diagnostic.json) recorded 36/40 and a passing gate with the same four source conflicts, p50 55 ms, p95 2,537 ms, max 4,064 ms, 45 downstream calls, 14 claim calls and four retries. It is a separate profile. The small default timing change with identical correctness and call counts does not establish an improvement in cold-path throughput.

### Filing root cause and operational handling

`workflow.apply_action` binds the approved draft to one immutable body and calls `State.begin_filing` before `Gateway.file`. `filing_operations` persists the hash and state, `active_filings` holds the immutable body and enforces a tenant/member reservation, and `filing_attempts` records dispatch and status without payloads or credentials. `recovery.recover_one` claims a recovery slot transactionally, checks the stored hash and replays only the original bytes and key through the gateway. A valid 201 or a validated replay receipt supports FILED under the durable contract. The recovered receipt replaces the pending confirmation result. A missing capability, bad local evidence or exhausted retries goes to MANUAL_REVIEW. The slice runs as one application process. Distributed worker leases and protected audit retention remain production work.

The mock's `Store.__init__` starts with an empty idempotency dictionary, and `Handler.do_POST` inserts the record and key before returning the delayed 503. An isolated contract probe observed first POST 503, replay 200 with `Idempotent-Replayed: true`, different body 422, and exactly one matching grievance. After restarting the downstream process, a read found zero matching records. The probe made no post-restart write. The mock exposes a member grievance list but no operation-key lookup, no server generation indicator, and no retained deduplication window. An application restart alone does not erase a still-running mock's keys. However, the application cannot establish that the same mock instance is still serving. The default worker therefore does not replay unknown operations after a restart. Inline 503 replay uses the documented mock behavior within the bounded foreground request.

For manual review, an authorized operator should inspect the protected ledger and obtain authoritative downstream evidence linking the original approved operation to a receipt. Keep the tenant/member reservation while evidence is unavailable. Similar free text, category or timing from the list does not prove identity. The slice does not provide an operator override or allow filing a replacement to clear an uncertain record.
